# GO ELO 安卓版 · 首版设计

日期：2026-09-17  
状态：用户已确认本稿，并要求开始编写实施计划。尚未创建安卓工程。

## 1. 产品定位与已确认决定

为自己使用的个人围棋成长 App。核心是快速记录对局、观察棋力变化和方便地备份换机。

| 项目 | 已确认决定 |
|---|---|
| 使用对象 | 个人使用 |
| 产品方向 | 竞技成长型 |
| 酷炫的重点 | 页面显示、排版、配色和视觉质感 |
| 视觉方案 | A：黑金竞技 |
| 录入方式 | 对手段位＋当前段位内最近不超过 20 盘的战绩＋本局胜负 |
| 对手强度假设 | 对手这批对局所遇棋手的强度，统一等于其当前段位基准分 |
| 估分规则 | 按原始胜率反推，不做样本平滑 |
| 全胜／全败边界 | 段位基准分＋600／−600；0-0 使用基准分 |
| 段位基准 | 1 段 1100，每段增加 200，7 段 2300，9 段 2700 |
| 导出主要用途 | 备份与换机恢复 |
| 运行方式 | 完全离线，无需登录 |

## 2. 视觉设计

以已选择的 A 方案为参考：`go-elo-visual-directions.html`。

- 深色底层、暖金色强调、浅暖白正文；分数与主要操作拥有最高视觉权重。
- 首屏突出当前 ELO、距离目标的差值及趋势；使用金属色渐变、细线几何和清晰的卡片层次。
- 图表采用金色曲线和轻量面积填充，触摸后查看节点的等级分和对局序号。
- 录入、备份使用底部面板，减少页面跳转。
- 转场、按压、数值变化保持短促；尊重系统减少动画设置。
- 支持字体放大和不同手机宽度，正文与触摸区域按安卓实际尺寸实现。网页概念稿中的小号说明文字不直接作为正式版字号标准。
- 用胜／负文字和正负号表达结果，不只依赖颜色。

视觉稿中的三种导出选项是早期探索。本稿收敛后，首版首页右上角改为直接进入“备份”；表格和分享图片不列入首版。

## 3. 首版页面与功能建议

### 成长

显示当前 ELO、内部段位参考、目标进度、最近 20 盘胜率、当前连胜、历史最高分、走势和最近对局。支持最近 20／50／100 盘与全部走势。固定保留“记一盘”和“备份”入口。

段位是本 App 基准表下的参考，界面不把它称为已获得的平台正式段位。低于 1 段基准显示“低于 1 段基准”；超过 9 段基准显示“9 段基准以上”，不创造 10 段。

目标默认采用下一个基准分，也允许设置明确的目标 ELO。超过 9 段基准时使用自定义目标；已达到目标则显示“已达成”，不出现负的剩余分数。

### 分析

- 最近 20／50／100 盘与全部胜率、对局数和净 ELO 变化。
- 按对手当时输入的段位分组统计胜率，并展示各组盘数。
- 月度对局量、胜率和净 ELO 变化。
- 历史最高分、最长连胜。

所有指标只使用已有记录。首版不推断执黑／执白、失误原因或棋谱内容。无数据的指标显示“暂无”，不以 0% 代替未知。

### 对局

按顺序展示日期、对手段位、对手近期战绩、对手估算分、本局胜负和 ELO 变化。支持按对手段位、胜负、日期筛选；无日期的旧记录单独可筛选。

新格式记录支持更正对手段位、战绩和本局结果，或删除记录。更正／删除后重算后续新格式记录，相关统计同步更新。第一版不提供拖动调整历史顺序。

### 我的

初始 ELO、目标、备份与恢复、旧版导入、计算规则说明。首版只维护一个本地个人档案；显示名称可修改，不提供账号注册。

首次使用可输入初始 ELO，或通过段位填入基准分，也可选择导入旧数据。导入后，旧历史的衔接分数以导入预览确认的值为准。

## 4. 极速录入与计算规则

### 输入流程

1. 点击“记一盘”。
2. 选择对手段位，默认沿用上次段位。
3. 输入本局开始前、对手当前段位内的近期战绩，例如 `11-8`。
4. 实时显示对手估算 ELO，以及本局赢／输各自的预计变化。
5. 点击“我赢了”或“我输了”，保存并返回成长页。

胜负数为非负整数，总盘数必须不超过 20。接受短横线或中文横线，允许分隔符两侧空格。没有近期战绩时可输入 `0-0`。每次打开清空战绩输入，防止误把上一位对手的战绩复用；未输入时不能提交。

日期和时间自动记录。保存期间禁用重复提交；数据库保存成功后才更新页面并显示撤销入口。撤销仅针对刚保存的一盘，且有下一次数据修改后即失效。

### 对手等级分

设段位为 d，胜场为 W，负场为 L：

```
B(d) = 1100 + 200 × (d - 1)

W > 0 且 L > 0：Ropp = B(d) + 100 × log10(W / L)
W > 0 且 L = 0：Ropp = B(d) + 600
W = 0 且 L > 0：Ropp = B(d) - 600
W = 0 且 L = 0：Ropp = B(d)
```

不加平滑、不按盘数加权。因而 1-0 和 20-0 都使用＋600；3-1 和 15-5 得到相同修正。600 仅处理全胜／全败，其余有效战绩严格使用公式。

### 自身等级分

建议沿用旧版 K=20 作为首版固定规则。对手估分只用于这一盘，不建立会随本人对局结果变化的对手评分档案。

```
E = 1 / (1 + 10^((Ropp - Rself) / 400))
Δ = 20 × (S - E)       // S：赢为 1，输为 0
Rnext = Rself + Δ
```

计算使用完整浮点精度，中途不取整；显示时统一取 1 位小数，备份保留原始计算值和输入。与旧 C++ 代码中预期胜率函数接收整数的行为存在差异，新记录采用精确计算，导入的历史分差保持原值。

每盘保存原始输入、估算对手分、本方赛前／赛后分、分差和规则版本。新临时对手记录使用 `elo-v3`（基准表为 1 段 1100、系数 100）；历史 `elo-v1/v2` 记录仍按各自规则重放，避免升级悄悄改变历史。

## 5. 离线存储与备份恢复

### 本地存储

对局和设置保存在本机数据库。运行不依赖网络、账号或云服务，首版不主动接入网络。用户主动通过其他 App 分享备份，是系统分享行为，不构成本 App 的云同步。

记录采用稳定 ID 和明确的顺序，不用姓名或文件行号作为数据身份。

### 一键备份

首页右上角点击“备份”，生成单个 `GO-ELO-日期-时间.goelo.json` 文件，然后选择“保存文件”或“分享”。内容包括：

- 备份格式版本、导出时间、应用版本。
- 本地档案、初始分、目标和可恢复设置。
- 全部原始对局、规则版本、已计算分值。
- 旧数据来源信息、旧历史的原始分差与衔接信息。

先读取一致的数据快照并生成完整文件，再通过系统文件选择器保存，或交给系统分享面板。取消保存不改变应用数据；保存失败不显示成功。分享只显示“已交给分享面板”，不声称接收方已经收妥。

文件格式独立于数据库内部结构，便于未来应用升级后继续恢复。首版使用可读 JSON，不做密码加密。

### 恢复

选择文件 → 检查格式及数据有效性 → 预览备份时间、个人名称、对局数量、当前 ELO → 确认整体替换 → 恢复成功。

- 先在临时内存／文件中完成解析，检查版本、有限数字、ID 唯一性、战绩范围和记录关联。
- 新格式记录按已知规则重放并核对结果；旧历史按保留的原始分差与衔接数据验证。
- 文件损坏、未知的更高格式版本或规则不支持时，说明原因并保持当前数据不变。
- 替换前必须成功生成本机恢复快照；数据库采用事务更新，失败回滚。
- 首版不合并两份档案。重复恢复同一个文件不会叠加对局。
- 本机保留最近 3 个恢复／导入前快照，用于撤销覆盖。它们用于本机恢复，换机仍使用手动导出的文件。

## 6. 旧版数据迁移

阅读依据为 `GO_ELO/mygui/Project1/Project1/` 下的 `goplayer.h`、`ELO_Calculate.cpp`、`PlayerInputWindow.h`、`FileManager.h` 和 `main.cpp`。邻近的 `GOELO` 与 `GO_ELO_PLUS` 只用于了解历史背景；不把其 README 声称的能力视为本目录现有实现。

旧数据只包含姓名、棋力／当前分数，以及对局双方、结果和分差，缺少可靠日期及本方案要求的对手当时战绩。因此迁移遵循以下边界：

1. 用户选择 `players.txt` 与一份权威对局文件，指定自己的棋手身份。支持 `games.txt` 或个人 `mygame.txt`，不默认把两个文件叠加导入。
2. 优先按 UTF-8 读取，必要时允许选择 GB18030。先预览解析结果与异常行，不能静默跳过数据。
3. 按用户身份筛选本人对局；若本人位于第二方，要反转结果和分差视角。保留原有行序，不凭内容相同就删除重复行，因为同样的对局描述可能真实发生多次。
4. 保留历史分差，使用已确认的当前分和累计分差建立历史衔接。预览显示推导的历史起点、记录数量与最终分；若原始文件不一致，允许调整导入集合或衔接分，确认前不落库。
5. 缺失日期标记为“日期未知”，不纳入月度统计。缺失对手战绩保持未知，不填成 0-0。
6. 旧历史作为保留区间，第一版可查看、备份和整体重新导入，不提供逐盘重算修改；新录入区间可编辑并重算。这样不会用猜测出来的对手分重写旧历史。

旧导入若只有个人对局集合，就只展示该集合；新 App 不会凭空补齐旧版未写入的对局。导入整体替换前同样创建恢复快照，并显示预览。

## 7. 实现路线比较与建议

| 路线 | 适配当前目标的理由 | 取舍 |
|---|---|---|
| Kotlin＋Jetpack Compose＋Room，推荐 | 聚焦安卓原生界面与本地数据；系统文件选择和分享直接接入 | 需要新建安卓工程，重写 UI 与业务实现 |
| Flutter＋本地数据库 | 也能制作定制视觉，适合后续明确需要多个平台时考虑 | 当前只有安卓需求，跨平台收益暂时用不上；文件操作仍需平台集成 |
| 延续 C++／ImGui，适配安卓 | 可保留一部分现有 C++ | 旧界面使用 Win32／DX11，布局和文件管理仍需重做；不推荐用于本次以手机视觉与体验为主的升级 |

推荐原生路线是针对本项目需求的判断，不代表其他方案不能实现同样的视觉。

采用一个安卓应用工程，按职责分包即可，首版不必拆成大量构建模块：

- UI：黑金视觉组件、四个页面、录入／备份面板；展示状态并提交用户动作。
- 领域计算：纯 Kotlin 的估分、个人 ELO 更新、历史重放和统计，不依赖 UI 或文件 API。
- 本地数据：Room 数据库和仓库，事务写入、唯一 ID、顺序和格式升级。
- 文件服务：备份编码／解码、旧版解析、系统文件保存与分享。解析器不直接写正式数据库。

数据流：输入校验 → 领域计算 → 数据库事务 → 页面观察数据变化。恢复流：临时解析校验 → 预览 → 快照 → 事务替换 → 页面刷新。

当前网页只承担视觉讨论，不作为正式安卓 App 的 WebView 页面。工程和构建工具具体版本在实施计划阶段按本机环境选择兼容的稳定组合；设计不绑定某个临时版本号。

依据：

- [Android 官方 Jetpack Compose 介绍](https://developer.android.com/compose)：原生 UI、Kotlin、主题和动画支持。
- [Android 官方 Room 文档](https://developer.android.com/training/data-storage/room)：SQLite 抽象和数据库迁移。
- [Android 官方文档文件访问](https://developer.android.com/training/data-storage/shared/documents-files)：系统文件选择、创建和打开文档。
- [Flutter 官方架构概览](https://docs.flutter.dev/resources/architectural-overview)：跨平台框架与平台集成。

## 8. 验收重点

- 黑金首页、录入、分析、对局、备份页面在真实安卓手机上风格一致；字体放大、键盘出现和小屏幕时不遮挡必要操作。
- 无网络也能首次启动、录入、查看、备份到本地和从本地恢复。
- 计算覆盖普通战绩、相同比例不同盘数、全胜、全败、0-0、非法输入；例如 7 段 11-8 按当前规则估分约 2313.8。
- 录入失败不出现已保存状态，双击不生成重复记录。
- 修改／删除已保存的新格式对局后，所有后续新格式分数与从起点重放的结果一致。
- 备份后在全新安装的数据环境中恢复，原始记录、顺序、分数和设置一致。
- 取消导入、损坏文件、未知版本、快照失败和恢复失败均不破坏现有数据。
- 用旧文件副本验证导入；未知字段不伪造，原文件不改写。
